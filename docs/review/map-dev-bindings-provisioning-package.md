## Legacy session accessor contract

Pinned primary source: [weweb-assets/plugin-supabase-auth at b67f2e2d](https://github.com/weweb-assets/plugin-supabase-auth/blob/b67f2e2d9b5220f9ba0c3f824bfa36b94c6cc645/src/wwPlugin.js), package 3.1.0, supabase-js 2.50.3. The source creates `publicInstance` in `load` and shares it with the data plugin. `refreshAuthUser` obtains a session from that instance; it also writes a cached user `_session`. `refreshSession` writes another cached copy. This upstream commit is not evidence of the version installed in Investscape Dev.

The scoped host should receive the verified existing public client, with an explicit expected Dev issuer. Its fresh read is `wwLib.wwPlugins.supabaseAuth.publicInstance.auth.getSession()`, returning only transient `{issuer, subject: session.user.id, expiresAt: session.expires_at, accessToken: session.access_token}` into the existing transport. Session metadata is client input, not server authority. Do not use cached `user._session`, call `fetchUser` to obtain a token, create a second client, inspect storage, decode a token as authorization, or use `privateInstance`.

Subscribe directly to that same client's `auth.onAuthStateChange`; notify transport invalidation on sign-out, account replacement, token refresh and session loss. Defer notification out of the Auth callback using a cancellable task; do not await another Supabase API call inside the callback. Unsubscribe the returned `data.subscription` and cancel pending tasks on host teardown. If the public client changes, tear down the old registration and require a freshly verified replacement. Existing component/transport cancellation and final account recheck remain required. No fallback to modern integration Auth actions or provider replacement is proposed.

The connector's current wewebAuthContext documentation describes WeWeb Auth only; its integration actions require the corresponding provider. Those documents cannot establish this legacy getter's availability in the installed build. A non-secret plugin version/release and rendered-environment project mapping are the missing confirmation; no token or identity is needed. Host installation is still pending.

The external receipt must also pin the final candidate SHA256, recorded in package.json. This is a separate map ledger; the Lighthouse runner/ledger is untouched. An owner can change its objects, so the ledger is operational traceability, not an independent tamper-proof record.

Final assertions check owner, forced RLS, invoker functions, disabled role attributes and gateway schema/table/function denial before commit. Future object creation still requires explicit revokes; absent recorded defaults are insufficient. The receipt guard prevents accidental execution and is not authorization or project attestation: target selection must be confirmed outside SQL.
